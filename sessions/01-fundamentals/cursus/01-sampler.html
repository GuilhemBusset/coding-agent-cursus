Act I · The sampler

What is a language model, exactly?

One equation, then everything an agent is built on: tokens, a distribution, attention, how the model is made, and what it cannot know.

  1. One conditional distribution, written on the board.
  2. Tokens and IDs; the strawberry demo and the pivot to code.
  3. A forward pass gives probabilities; sampling picks one token.
  4. Attention as a soft lookup.
  5. Pretraining, post-training, RL with verifiable rewards.
  6. Cutoff, hallucination and what is at stake in OR.

Four labs along the way. Open them when the slide says so.

Speaker notes · 1 min

Talk track: by the end of this act everyone should hold a correct, unglamorous picture: a model is a function that returns a probability for the next token, and a sampler that draws one. Everything clever happens around that loop, which is Act II.

Say that each idea is followed by a widget they use on their own laptop, and that the four labs work offline from the course folder.

Background for you, not for the slides: Andrej Karpathy, Deep Dive into LLMs like ChatGPT (YouTube) covers the same arc from pretraining data to RL at greater length.

Transition: “Let us start with the only equation of the session.”

01 · One equation

A language model is one conditional distribution, used again and again.

p(xt | x<t)

xt is the token at position t. x<t is every token before it, x1 … xt−1: the whole context, not just the last word.

p(x1, …, xT) = ∏t=1T p(xt | x<t)

The chain rule factorizes the joint distribution of a whole sequence into these conditionals, exactly. Autoregression is the modelling choice: one network computes every factor, and generation draws x1, then x2 given x1, and so on.

Boundaries

At t = 1 the context x<1 is empty; in practice the model sees a beginning-of-sequence token there.

An end-of-sequence token is part of the vocabulary, so “stop here” is one more outcome and the length T is modelled too.

Speaker notes · 3 min

Write p(x_t | x_<t) on the board before you show the slide and leave it there all session; Act II and the labs come back to it.

Talk track: read it aloud as “the probability of the next token given everything before it”. Then write the product underneath: the probability of a whole text is the product of these conditionals. This is the chain rule of probability, a factorization that holds for any joint distribution, so it is not an approximation. The approximation is the network that computes each factor.

Mention the two boundary conventions: an empty context, or a BOS token, at t = 1; and an EOS token so the model can choose to stop.

Predict question: “Is writing a text one token at a time a simplification that loses something?” Answer: no, the factorization is exact; what limits the model is how well it learns each conditional.

Transition: “What exactly is an x_t? Not a letter, and not quite a word.”

02 · Tokens

The model reads integer IDs, not letters.

A token is a word, a piece of one, a few digits or a character. Each becomes its integer ID: a sentence is a list of numbers.

The ID carries no spelling. A model can only pick up which letters a token contains indirectly, from training text, so spelling and letter counting are hard for it, not impossible.

Token ID recorded in fixtures/next_token.json with the GPT-2 tokenizer, openai-community/gpt2 at revision 607a30d783dfa663caf39e06633721c8d4cfcd7e, 2026-10-10.

03 · One forward pass

One forward pass gives a distribution, not an answer.

The network returns one score zi per vocabulary entry. Then:

p = softmax(z/T)

A sampler draws one token from p and appends it. Temperature T < 1 sharpens towards the top token (argmax as T → 0); T > 1 flattens.

Name it: System 1. Each token costs one fixed pass through the network, with no extra passes for a harder token.

Probabilities at T = 1 over the full vocabulary, from the logits and log-sum-exp recorded in fixtures/next_token.json (GPT-2 small, 2026-10-10). The top 20 hold 45.7% of the mass.

Speaker notes · 3 min

Talk track: GPT-2 does not answer “Paris”. It returns probabilities, and “ Paris” is fifth at 3.2%, behind “ the” at 8.5%, because “The capital of France is the city of Paris” is also a good continuation. The answer appears only when a sampler draws.

Write softmax(z/T) next to the equation on the board: divide the scores by T, exponentiate, normalize. Low T piles mass on the top token; T → 0 is argmax, the same token every time; high T spreads it out.

Name System 1 now: one pass, fixed compute per token for a given model, context and configuration. It does not mean constant latency: a longer context makes each pass slower. It means there is no step where the model decides to think longer about a hard token.

04 · Why outputs differ

Same prompt, different answer: sampling, not a bug.

  • Each answer is a draw. A flat distribution gives different outputs; a peaked one can repeat itself. Sampling allows a difference; it does not guarantee one.
  • A fixed seed or argmax reproduces locally, as in the tiny-LM lab.
  • Neither agent CLI lets you fix a seed, and even greedy decoding on shared GPU servers can drift: batching can change the order of floating-point additions.

05 · Inside the pass

Attention is a soft database lookup.

A database matches a query against keys and returns the one value whose key matches. In attention, the current token’s query q is scored against the key ki of every earlier token and itself; softmax turns the scores into weights that sum to 1, and the output is the weighted average of their values vi.

  1. Query What am I looking for? one vector per token
  2. Match keys Score q·ki/√d softmax turns scores into weights
  3. Blend values Σi wi vi a soft, not exact, lookup

softmax(qKT/√d)·V

Causal: a token looks only at itself and earlier tokens, which is what keeps each factor p(xt | x<t). GPT-2 small runs 12 heads in each of 12 layers.

Speaker notes · 2 min

Talk track: a dictionary lookup is hard: exact key, one value. Attention makes it soft and differentiable: every key gets a similarity score, softmax turns the scores into a probability measure, and the output is the expectation of the values under it. d is the key dimension; dividing by √d keeps the scores from growing with it.

This is the only mechanism slide of the act. Each head learns its own queries, keys and values, and stacking layers lets later lookups use earlier results. The lab shows a real GPT-2 head linking “it” to “animal”.

Transition: “Drag a query and watch the weights move.”

06 · How a model is made · 1/3

Pretraining: predict the next token of a vast amount of text.

  • Training minimizes −log p(xt | x<t) over the corpus. That quantity is a code length: with arithmetic coding, a better predictor is a better lossless compressor.
  • The weights are far smaller than the text they read, so they cannot keep it verbatim. What survives is what helps predict. Think of the model as a lossy compression of its training text.
  • The result is a base model: a document continuer, not an assistant.

The paper is about prediction as lossless compression of a sequence. “Lossy compression” of the corpus is our metaphor for what the weights keep, not a result of the paper.

Source: Grégoire Delétang et al., Language Modeling Is Compression, arXiv 2309.10668 (2023), abstract.

Speaker notes · 2 min

Talk track: the loss on the board is the number of bits the model would need to encode the text. Delétang et al. state in their abstract that predictive models and lossless compressors are equivalent, and that a large language model trained mostly on text is also a strong general-purpose compressor.

Our framing on top: the weights are a lossy compression of the training text, Karpathy’s “lossy zip file of the internet” in the deep-dive video. Frequent regularities survive; rare facts may survive partially or not at all, and the model cannot tell which.

Transition: “A base model continues documents. Ask it a question and see what you get.”

06 · How a model is made · 2/3

Post-training turns a document continuer into an assistant.

Fine-tuning on conversations, then on preferences, teaches the format: answer, then stop. It changes behaviour; it adds no fact checker.

Speaker notes · 3 min

Predict question, before you reveal the right column: “Same question, a model of the same size. What does the base model write after it?” Many will expect a plain answer.

Talk track: the base model gets the capital right, then keeps going because the most likely document is a quiz page: it invents the next question and a false answer about New Zealand. The base excerpt shown is the first three lines of its 48 tokens; it was still writing when the limit cut it off. The instruct model, the same architecture after post-training, answers and emits end-of-sequence.

Post-training is supervised fine-tuning on conversations in a chat template, then preference tuning. It teaches the role and the format. It does not make the model check facts: the same weights could still produce the New Zealand line in another context.

Transition: “The newest stage adds a reward that can be checked by a program.”

06 · How a model is made · 3/3

RL with verifiable rewards: the reward comes from a checker.

  1. Task A checkable problem maths with a known answer, code with tests
  2. Sample Many attempts drawn from the model
  3. Verify A program scores each reward 1 if it passes, else 0
  4. Update Reinforce what passed those tokens get more likely

The model learns to pass the checker, not to be right. A weak checker gets gamed; Act V shows how.

Term from Nathan Lambert et al., Tülu 3: Pushing Frontiers in Open Language Model Post-Training, arXiv 2411.15124 (2024). Rule-based rewards at scale: DeepSeek-AI, DeepSeek-R1, arXiv 2501.12948 (2025).

Speaker notes · 2 min

Talk track: preference tuning needs a judge, human or model. RLVR replaces the judge with a verifiable reward: a program that checks the final answer or runs the tests. The model samples many attempts, the passing ones are reinforced, and over many rounds the model gets better at producing answers that pass.

Link to OR: our problems are unusually checkable. Feasibility of a plan and its objective value can be recomputed without trusting whoever produced them. That is why agents can be trusted more here, and why our checks must be honest.

Transition: “Three things no training stage fixes.”

07 · Limits · 1/3

Knowledge cutoff: the weights stop at a date.

  • The training text was collected up to a cutoff. After it, the weights hold nothing, and the model may not know its own cutoff precisely.
  • Ask about a newer library version and you get a fluent answer about an older one.
  • Context can carry newer facts. What the agent reads at run time (your files, the docs, a search result, a tool’s output) is part of x<t.
Speaker notes · 1 min

Talk track: no vendor cutoff date on the slide on purpose; they change with every model and a date here would age badly. The point is structural: the weights are frozen at training time.

The practical fix is the context: an agent that reads the installed package’s docs or runs --help gets the current API, because those tokens are part of x_<t.

Transition: “Even before the cutoff, nothing guarantees an answer is true.”

07 · Limits · 2/3

No truth oracle, so hallucination is structural.

  • Pretraining rewards likely text, not true text. Nothing in p(xt | x<t) consults the world: there is no truth oracle inside the model.
  • So a false continuation is produced the same way as a true one, and reads the same. Recall the base model: “New Zealand is the second largest country in the world.”
  • Structural does not mean always wrong. Models often get common facts right, and post-training can teach them to say “I don’t know”. It means any single answer can be wrong.

The check has to come from outside the model: tests, a source, a solver’s feasibility check.

Speaker notes · 2 min

Talk track: hallucination is not a bug that a later version removes. The objective is likelihood, and likelihood is not truth. Fluency is evidence of a good language model, not of a correct answer.

Predict question: “Can you tell the hallucinated line from the true one by how it reads?” Show the post-training slide again if needed: the Canberra line and the New Zealand line read the same.

Transition: “In our field, a wrong line reads just as well and still runs.”

07 · Limits · 3/3 · Illustrative

The OR stake: a flipped objective reads as fluently as a correct one.

Stated problem: open plants and ship to meet every customer’s demand at least total cost.

h.changeObjectiveSense(highspy.ObjSense.kMinimize)
h.changeObjectiveSense(highspy.ObjSense.kMaximize)

Both lines are equally fluent, both run, and the solver calls both results optimal. Only the first, minimize, matches the stated problem.

Read the model, not the status: check the objective sense against the problem statement.

Speaker notes · 2 min

Talk track: these two lines are invented for the slide, but the trap is real and you will meet it. In P00 the model sets the sense with h.changeObjectiveSense(highspy.ObjSense.kMinimize); the P00 lab’s flipped-sense variant changes only that to kMaximize, and HiGHS still reports “optimal”, with an objective of 1085 instead of 485.

Predict question: “Which line would a model write if it had seen many profit-maximizing examples?” Either, with similar fluency: nothing in the text tells you which one is right except the problem statement.

Transition: “Let us name what we have seen all act.”

Close · System 1

Everything in this act was one forward pass: System 1.

  • One pass maps x<t to p(xt | x<t); a sampler draws one token.
  • Fixed compute per token: for a given model, context and configuration, the same layers run once per token, however hard the question.
  • Longer context makes a pass slower; it does not make the model think longer.

Next · Act II

Put the pass in a loop: let the model write tokens it then reads, call tools, run code and check results. That is how an agent spends more compute on a hard problem.

Speaker notes · 2 min

Talk track: point at the board one last time. The model is p(x_t | x_<t) plus a sampler. Each token gets a fixed amount of computation, System 1, fast and fluent, with no step where it decides to think harder about a hard token.

Be precise about “fixed”: a longer context costs more time per pass, but that is reading more, not reasoning more. For a given model, context and settings, the work per token does not adapt to difficulty.

Transition into Act II: “If one pass cannot think longer, how do reasoning models and agents solve hard problems? They run this pass in a loop. That is the next act.”
