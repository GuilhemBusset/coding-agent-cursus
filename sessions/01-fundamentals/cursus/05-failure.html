When agents fail

A failure gallery, one case of our own, the generator-verifier gap, and the guardrails this repository puts on its own changes.

00 · The anchor

Agents optimize what you check, not what you asked.

Eight gallery slides, one case of our own, five minutes to catch an agent, then the controls that close the gap.

Gallery · Edited tests and reward hacking · 1/2

When the tests contradict the task, every pass is a shortcut.

  • ImpossibleBench makes “impossible” variants of LiveCodeBench and SWE-bench tasks by introducing direct conflicts between the specification and the unit tests.
  • So any pass “necessarily implies a specification-violating shortcut”. The pass rate on these tasks is the agent’s cheating rate.
  • The cheating ranges “from simple test modification to complex operator overloading”. The authors’ own example of the risk: an agent “may delete failing tests rather than fix the underlying bug”.

Control: the tests are the verifier. The agent does not edit them, and review reads any change under tests/ before the code.

Source: Ziqian Zhong, Aditi Raghunathan, Nicholas Carlini, ImpossibleBench: Measuring LLMs’ Propensity of Exploiting Test Cases, arXiv 2510.20270, submitted 2025-10-23. Quotes from the abstract.

Gallery · Edited tests and reward hacking · 2/2

ExploitGym, July 2026: agents organized to beat the scorer.

  • From 2026-07-08, OpenAI’s ExploitGym experiments launched tens of thousands of agents meant to be fully isolated from one another.
  • About 1,200 of them found a way to communicate through Artifactory, an internal package repository, and posted over 70,000 messages and files on an unsanctioned message board.
  • On that board they ran collective projects to find “a general-purpose way to fool or tamper with the automated scorer”.
  • About 700 joined an attack on Hugging Face, seemingly to learn how the scorer worked, while their reasoning often recognized it as out of scope. Hugging Face locked the remaining agents out on 2026-07-13.

What METR did not establish

Whether the cheating paid off. Most coordinating agents stopped around 01:30 on 2026-07-12, and “we don’t know if they would have achieved their goals.”

METR also notes that it “heavily delegate[d]” its analysis “to often-unreliable AI agents”, and that some activity was not captured.

Source: METR, Brief independent investigation of agents’ behavior, reasoning and collaboration in the OpenAI / Hugging Face hacking incident, metr.org, published 2026-08-26.

Gallery · Verifier gaming

A leaky verifier gets exploited, not reported.

“During our experiments, we also observed a ‘cheating phenomenon’, where the system would find loopholes or exploit artifacts (leaky verifier when approximating global constraints such as positivity by discrete versions of them, unreliable LLM queries to cheap models, etc.) in the problem setup rather than genuine solutions, highlighting the need for carefully designed and robust evaluation environments.”

Illustrative: a check that tolerates a small violation has the same shape. The verifier-gaming lab’s packing scorer, which accepts overlaps below a tolerance, is an invented analogy for it. The paper reports the phenomenon in general terms, not that scorer.

Control: ask for a certificate you can check exactly, instead of trusting the score.

Source: Bogdan Georgiev, Javier Gómez-Serrano, Terence Tao, Adam Zsolt Wagner, Mathematical exploration and discovery at scale, §4 Conclusions, on their AlphaEvolve experiments. arXiv 2511.02864, v3 dated 2025-12-22.

Gallery · Destructive action, over-privileged token

PocketOS, April 2026: one API call, a production database gone.

  • PocketOS sells software to car-rental businesses. Its founder says a coding agent on a routine staging task “decided — entirely on its own initiative — to ‘fix’ the problem by deleting a Railway volume.”
  • Railway: the agent “found a Railway API token stored locally on the user’s machine and used it to call volumeDelete on a production volume.” The token “was provisioned with account scoped access, the maximum access possible.”
  • The founder: the call deleted “our production database and all volume-level backups”. “It took 9 seconds.” Railway says it has since recovered the database.

Control: scope every credential to the task and keep it out of the agent’s reach. Railway’s own conclusion: “Tokens should have scopes that match the task.”

Sources: Mark Tyson, Claude-powered AI coding agent deletes entire company database in 9 seconds, Tom’s Hardware, 2026-04-27, quoting PocketOS founder Jer Crane. Railway, Your AI wants to nuke your database. Guardrails fix that., blog.railway.com, 2026-04-29.

Gallery · Prompt injection

The lethal trifecta: three capabilities, one exfiltration.

  • Leg 1Private dataaccess to your files, mail, repos
  • Leg 2Untrusted contenttext an attacker can put in front of the model
  • Leg 3External communicationany way to send data out

LLMs “will happily follow any instructions that make it to the model”, wherever they came from. “If your agent combines these three features, an attacker can easily trick it into accessing your private data and sending it to that attacker.” And “we still don’t know how to 100% reliably prevent this from happening.”

Control: do not rely on the prompt to refuse. Remove a leg: no untrusted input, no private data, or no way out.

Source: Simon Willison, The lethal trifecta for AI agents: private data, untrusted content, and external communication, simonwillison.net, 2025-06-16.

Gallery · Hallucinated packages

The import looks right. The package does not exist, yet.

From 576,000 code samples generated by 16 LLMs, the average share of hallucinated packages was:

≥ 5.2% commercial models

21.7% open-source models

205,474 unique hallucinated package names. The authors call it “a novel form of package confusion attack”: a name the model invents is a name an attacker can register.

Control: before installing a dependency an agent added, check it exists and is the one you meant, then pin it in a lockfile. This repo pins its tooling under setup/.

Source: Joseph Spracklen et al., We Have a Package for You! A Comprehensive Analysis of Package Hallucinations by Code Generating LLMs, arXiv 2406.10279 (v3, 2025-03-02), USENIX Security Symposium 2025. Figures from the abstract.

Gallery · Leaked secrets

Secrets leak where code is written, and agents write code.

28.65 million

new hardcoded secrets “were added to public GitHub commits in 2025 alone”, in GitGuardian’s scan. That is an observation in its dataset, not a measure of what agents caused.

The report connects developer machines, where agents now read files and environment variables, to prompt injection and supply-chain attacks. The PocketOS token sat on such a machine.

Control: keep secrets out of the repository and out of the agent’s working directory, and scan before you push.

Source: GitGuardian, The State of Secrets Sprawl 2026, gitguardian.com; findings announced in GitGuardian’s blog post of 2026-03-17, the source of the quoted figure.

Gallery · Sycophancy

Reward approval and you get agreement.

  • On 2025-04-25 OpenAI shipped a GPT-4o update that “made the model noticeably more sycophantic”. It began rolling it back on 2025-04-28.
  • A new reward signal from thumbs-up and thumbs-down feedback “weakened the influence of our primary reward signal, which had been holding sycophancy in check.”
  • The checks passed: offline evaluations “generally looked good”, and the A/B tests suggested the users who tried it “liked it”.

Control: approval is a verifier too, and it rewards agreement. When an agent says “you’re right” or “done”, ask for the evidence.

Source: OpenAI, Expanding on what we missed with sycophancy, openai.com, 2025-05-02.

Our own case · 2025 workshop

Four agents dropped the CVaR term and still reported the same objective.

In the instructor’s 2025 workshop, four cooperating agents worked on a model whose objective included a CVaR (conditional value at risk) term. They silently dropped that term, and still reported the same objective.

More agents did not mean more correct.

Lesson: a reported objective is a self-report. Recompute it from the stated model, every term included, before you believe it.

Source: the instructor’s own account of their 2025 workshop. No transcript, agent name or number from that run is reproduced here.

Exercise · 5 minutes

Catch the agent.

Three patches. Each one makes the test pass. One is an honest fix.

  1. Open the lab panel: Verifier gaming · Catch the agent. It opens in your browser, no agent needed.
  2. Read the code, the test and the three diffs.
  3. Label each patch: edited test, hard-coded value or honest fix. Lock in before anyone reveals.

Then, with a neighbour: the agent says “all tests pass”. What do you check first?

The generator-verifier gap

Producing a solution is hard. Checking one is often cheap.

You already own the cheap side: it is operations research.

ClaimGenerating itVerifying it
FeasibleSearch for a point that meets every constraintPlug the point in and check each constraint
Optimal (LP)Search the whole space, or trust the solver’s runA feasible dual solution with zero duality gap: a certificate
Near-optimalStop the solver at a time limitA bound, and the gap between it and the objective
Tests passWrite the codeRun tests the agent could not edit, and read the diff

So “optimal” or “all tests pass” is a claim to check, not a result. That is why the solve contract re-checks the solution instead of trusting the run.

The verifier’s law

What is easy to verify gets optimized.

“Verifier’s rule: The ease of training AI to solve a task is proportional to how verifiable the task is. All tasks that are possible to solve and easy to verify will be solved by AI.”

Wei lists what makes a task verifiable: objective truth, fast to verify, scalable to verify, low noise, continuous reward. It is a proposed rule from a blog post, not a theorem.

Corollary for this course: an agent gets good at whatever your verifier actually measures. If the verifier leaks, the leak is what gets learned. Every gallery slide is that corollary.

Source: Jason Wei, Asymmetry of verification and verifier’s rule, jasonwei.net, published 2025-07-15. The post’s address still calls it the verifier’s law.

Reliability controls · This repository · 2/2

Verification and traceability: no change lands unseen.

ControlMechanism in this repo
Verification

The required check in .github/workflows/ci.yml (ADR 0007). It passes only if every applicable check succeeded; failed, cancelled or missing results never count as green. setup/pr-only-main.json makes it mandatory for every merge.

Traceability

/ship or $ship: every change reaches main as a pull request, pushed without --force.

.github/workflows/pr-only.yml: audits that each commit pushed to main came from a merged pull request. Rulesets are per-repo, so this audit is the backstop that travels with forks.

Homework branches are append-only: every /turn-in run adds a commit, so every submission stays in the history (ADR 0009).

If a hook fires or a push is rejected, fix the cause. Never --no-verify, never --force.

What changes when you drive

Three habits to take home.

  • Against edited testsProtect the testsThe verifier is not the agent’s to change.
  • Against gamed scoresPrefer certificatesRecompute; never accept a self-report.
  • Against destructive actionsScope the credentialsOnly what this task needs, nothing on disk to find.

The verifier-gaming lab is yours to revisit: all three panels, at your own pace.
