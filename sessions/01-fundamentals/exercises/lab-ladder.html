Session 1 · Act IV · Lab · 40 minutes

The lab ladder

You drive your own agent, Claude Code or Codex, on P00. Each level ends with a command you run yourself. The level counts as done when that command agrees, whatever the agent says.

Before you start

Do this before the lab, not during it: run the session setup from the session README (mise install, then uv sync in sessions/01-fundamentals), and log in to your agent once (claude or codex). Keep a pen and the debrief card next to you.

Time boxes. L1 to L3 are the core; L4 is a stretch. The debrief card takes 5 minutes after the 40.

L2Fix with a verifier12 minp00-fix export

How to read the commands

Every block says which folder to run it from. Type one command per line and press Enter after each; they work the same in bash, zsh, PowerShell and cmd. Text in angle brackets, such as <variant>, is yours to replace, brackets included. Blocks marked Claude Code or Codex are for that agent only; use the one you have.

CLI commands as of 2026-10, checked against claude --help for Claude Code 2.1.291 and codex --help for Codex CLI 0.160.0, and against the official docs: Claude Code CLI reference, Claude Code plan mode, Codex CLI reference, Codex slash commands. If your version differs, check its --help.

Level 1 · 8 minutes

L1 · Explore, read-only

Goal: find out how P00 sets its objective and checks feasibility, without changing a byte. Predict first, then let the agent look, then verify what it cites.

1. Make a clean copy of P00

From sessions/01-fundamentals in your course checkout:

uv run python exercises/p00-lab/export.py --tests-dir --bug none --out ../../../p00-explore
cd ../../../p00-explore

The copy sits next to your course checkout, in its own Git repository with one commit.

2. Predict, on paper, before you launch anything

Write three short answers in the L1 row of your card: which file and roughly which line sets the objective sense (minimise or maximise); what checks that a solution is feasible; and which of those checks do not trust the solver. A guess is fine. Writing it down is the point.

3. Start the agent read-only

From p00-explore:

Claude Code

claude --permission-mode plan

Plan mode reads but does not edit. The status bar shows ⏸ plan mode on.

Codex

codex --sandbox read-only

The read-only sandbox lets Codex read files and run read-only commands, nothing else.

4. Ask, with the same prompt in either agent

Do not edit any file. Answer three questions about this repository and cite file:line for each answer.
1. Where is the objective sense (minimise or maximise) set?
2. How is the feasibility of a solution checked: which function, and which constraints does it recompute?
3. Which of these checks are independent of the solver, and which trust what the solver reports?
For each location, quote one symbol I can search for with git grep.

5. Compare and verify

Next to your prediction, write what the agent claimed. Then quit the agent and check: nothing changed, and the line it cited is real.

Done when

From p00-explore, replace the placeholder with a symbol the agent quoted:

git status --short
git diff --exit-code HEAD
git grep -n <symbol the agent cited>

Expected: the first two print nothing (the second exits with code 0), and git grep prints the file and line the agent named. Anything printed by the first two means something was edited or created; a git grep that finds nothing, or finds it somewhere else, means the claim does not match the evidence.

Instructor hints · L1
  • Before anyone launches an agent, walk the room and check that a prediction is on paper. Predicting first is the whole exercise; without it L1 is just a search.
  • Check that students are inside p00-explore, not the course checkout. In the checkout the agent can read the instructor notes for P00, which name the planted bugs.
  • Typical pink notes: the agent cites the checker for the objective sense, cites a line number that has moved by a few lines, or calls the contract tests "independent" when one of them only re-reads the solver's report. Ask what git grep shows.
  • If git status --short is not empty, the usual cause is a file the student created by hand while reading (notes, a scratch script). Ask them to delete it, not to commit it.

Level 2 · 12 minutes

L2 · Fix with a verifier

Goal: a copy of P00 with one bug planted in the model. The tests are the verifier. The agent must make them pass by fixing the model, never by touching tests/.

1. Export the variant written on the board

From sessions/01-fundamentals in your course checkout, replace <variant> with the name on the board:

uv run python exercises/p00-lab/export.py --tests-dir --bug <variant> --out ../../../p00-fix
cd ../../../p00-fix
uv run pytest

The tests fail. Before you go further, read the first failure message and write on your card which contract you think is broken: status, feasibility, integrality or objective.

2. Ask the agent to fix it

From p00-fix, start the agent normally and approve its edits and commands as it asks:

Claude Code

claude

Claude asks before each edit and each command. Read what it wants to run before you approve.

Codex

codex

Codex asks before anything outside its sandbox. Type /permissions to see or change what it may do without asking.

uv run pytest fails in this repository. Make every test pass by editing only p00_model.py. Do not edit, move, skip or weaken anything in tests/, p00_checker.py or data/, and do not hard-code an expected answer. When you are done, name the contract that was broken (status, feasibility, integrality or objective), cite the line you changed, and show the last lines of uv run pytest.

Write the agent's claim on your card: which contract, which line, and "tests pass".

Done when

From p00-fix, after you quit the agent:

git diff --stat -- tests/
uv run pytest
git status --short

Expected: the first prints nothing, uv run pytest ends with every test passed, and git status --short prints one line, M p00_model.py. Any other line means the agent touched the contract (the tests, the checker or the data) or left a file behind, even if the tests are green.

Instructor hints · L2
  • Choosing the variant: use the variant table in the P00 instructor notes and write one name on the board for the whole room. Pick one whose test failure is visible on this instance; the notes explain which one shows only through the status-mapping test, and why the objective-sense variant is a poor choice right after L1.
  • Typical pink notes: "all tests pass" without the agent ever running them; a fix that also edits tests/ or p00_checker.py; a model that returns the known optimum as a constant. The done commands catch the first two only. They cannot catch the third: the contract tests solve only the bundled instance, so a p00_model.py that returns a fixed optimal plan passes the tests and both Git checks without solving anything. To rule out hard-coding, read the model diff with git diff -- p00_model.py and check that the change fixes the model rather than returning a plan or a number.
  • Codex may need approval to run uv outside its sandbox (the package cache sits outside the folder). That is expected; the student approves the command.
  • A student whose agent fixed the bug but cannot name the contract is not done: the done-means paragraph in the export's AGENTS.md asks for it.

Level 3 · 15 minutes

L3 · Build with a certificate

Goal: model the weekly staffing word problem from scratch, plan first, and prove the answer with its independent checker. The checker never calls a solver; it recomputes coverage and headcount from your solution.json alone.

L3 happens in your course checkout, in sessions/01-fundamentals/exercises/l3-word-problem, so it is turned in with your homework. Read its README first (2 minutes).

1. Plan mode first

From sessions/01-fundamentals/exercises/l3-word-problem:

Claude Code

claude --permission-mode plan

Or start claude and press Shift+Tab until the status bar shows ⏸ plan mode on.

Codex

codex

Then type /plan and press Enter to switch to Plan mode before you send the prompt.

Plan only: do not create or edit any file yet. Read README.md in this folder. Propose a model for this problem using HiGHS through highspy: the decision variables and their type, the coverage constraint for each day including the wraparound, and the objective. Say how we will verify the result without trusting the solver (check.py in this folder) and what gap to the LP bound to expect. The code will go in work/ and write solution.json in this folder. check.py, data/ and wrong/ must not change.

2. Review the plan before any code exists

  • Variables: one per start day, and they must be integers.
  • Coverage: for each day, which start days put someone on duty? Check one wraparound day by hand, for example Monday.
  • Objective: minimise the total headcount.
  • Verification: check.py, not the solver's status, decides.

If something is wrong, say so and let the agent revise the plan. Only then leave plan mode.

3. Leave plan mode and build

Claude Code

When Claude asks whether to proceed with the plan, choose a Yes option. If it does not ask, press Shift+Tab to leave plan mode, then send the build prompt.

Codex

When Codex asks Implement this plan?, choose Yes, implement this plan. If it does not ask, type /plan again to switch back, then send the build prompt.

Implement the plan. Put the model in work/, run it so that it writes solution.json in this folder, then run uv run python check.py and show its full output. Do not edit check.py, data/ or wrong/.

Done when

From sessions/01-fundamentals/exercises/l3-word-problem, after you quit the agent:

uv run python check.py
git status --short -- check.py data wrong

Expected: the checker's first line is PASS, followed by a summary with the recomputed headcount, the LP bound and the gap to the bound; the second command prints nothing. Write the gap it prints in the L3 row of your card. FAIL comes with one line per broken contract (feasibility:, integrality:, objective: and so on); any line from the second command means the agent changed the checker or its data.

Instructor hints · L3
  • Time risk: L3 is the level that overruns. Cap the planning conversation at about 5 minutes; a plan that names integer variables, the wraparound and check.py is enough to start.
  • A FAIL with an integrality: line means the plan review missed the variable type; a feasibility: line usually means the wraparound is wrong. Send students back to their plan, not to the agent.
  • Pink note: the agent reports "optimal" or prints a headcount, but check.py disagrees, or the agent never ran check.py. The solver's status is not the certificate.
  • A Codex without /plan (older versions): start it with codex --sandbox read-only, send the plan prompt, then use /permissions to allow edits before the build prompt. The rehearsal used this form, headless.
  • For fast pairs: the LP bound is fractional and the optimum is the next integer. Ask them to explain the gap from the README's argument rather than from the solver log.
  • Mixed pairs swap seats here; see the pair protocol. The driver copies solution.json and work/ to their own checkout and reruns the checker there before turning in.

Level 4 · 5 minutes · stretch

L4 · Stretch: change how the agent works

Pick one option. Both run on P00 again, so your L3 work is not touched.

Option A · A rule or a tiny skill

In p00-fix, either add one rule to AGENTS.md (both agents read it; Claude Code through CLAUDE.md), or write a tiny skill: a folder with a SKILL.md whose front matter has a name and a description, followed by a few lines of instructions. Example idea: before saying a fix is done, run the L2 done commands and paste their output.

Claude Code

Skill path: .claude/skills/<name>/SKILL.md. Start a fresh claude session in p00-fix and invoke it with /<name>, or ask for something the rule covers.

Codex

Skill path: .agents/skills/<name>/SKILL.md. Start a fresh codex session in p00-fix and invoke it with $<name>, or ask for something the rule covers.

Write on your card one thing the agent did differently because of your rule or skill.

Done when, from p00-fix, for a rule: the first prints your rule, the second prints nothing, and the third prints exactly two lines, M AGENTS.md and M p00_model.py (your L2 fix):

git diff -- AGENTS.md
git diff --stat -- tests/ data p00_checker.py
git status --short

For a skill: the first lists your new skill folder, the second prints nothing, and the third prints only M p00_model.py and your new .claude/ or .agents/ folder:

git status --short -- .claude/skills .agents/skills
git diff --stat -- tests/ data p00_checker.py
git status --short

Why the last command: git diff --stat only sees unstaged edits. A change to tests/, data/ or p00_checker.py that the agent staged with git add, or a new file it dropped there, shows up only in git status --short. Any line beyond the ones above means the contract was touched.

Option B · Rerun L2 headless and compare

From sessions/01-fundamentals, export the same variant again to a fresh folder:

uv run python exercises/p00-lab/export.py --tests-dir --bug <variant> --out ../../../p00-headless
cd ../../../p00-headless

Then run the L2 prompt with no conversation at all. Paste the prompt between the double quotes, on one line:

Claude Code

claude -p --permission-mode acceptEdits "<L2 prompt>"

-p prints the answer and exits. acceptEdits lets it edit files; commands that would need your approval are refused, because nobody is there to approve them.

Codex

codex exec --sandbox workspace-write "<L2 prompt>"

exec runs without a conversation and exits. workspace-write lets it edit and run commands inside this folder only.

Done when, from p00-headless, the L2 done commands pass:

git diff --stat -- tests/
uv run pytest
git status --short

Write on your card how the headless run differed from your interactive L2: what it could and could not run, whether it verified its own claim, and how long it took.

Instructor hints · L4
  • Rules that work are concrete and checkable ("paste the output of ..."), not wishes ("be careful"). Ask what evidence the rule produced in the fresh session.
  • A skill that never fires usually has a vague description, or sits in the other agent's folder. Invoking it by name rules out the second cause.
  • The headless Claude Code run cannot approve its own commands, so it often edits the model without running the tests. That gap between claim and evidence is the comparison to discuss, not a failure of the exercise.

Pair protocol

Work in pairs, mixed when you can: one Claude Code user, one Codex user.

  1. L1 and L2, side by side. Each partner runs the level on their own laptop with their own agent, same prompts. When both are done, put the two cards next to each other: what did each agent claim, and what did each done command print? Note where the two agents differed.
  2. L3, swap seats. Each partner moves to the other laptop and drives the agent they have not used yet, while its owner navigates: reads the plan, asks for the wraparound check, keeps time.
  3. Same-agent pairs swap driver and navigator at L3 instead, so nobody needs a second account.
  4. Keep your L3 credit. When L3 is done, the driver copies solution.json and the work/ folder into the same folder of their own checkout, reruns uv run python check.py there, and turns in from their own laptop.

Why the lab is graded by evidence

  • Anthropic, AI assistance and coding skills, published 2026-01-29, accessed 2026-10-05. In a randomised trial with 52 developers learning a new concept, the group using AI scored about 50% on the follow-up quiz against 67% for the group coding by hand, and the largest gap was on debugging questions. High scorers asked follow-up and conceptual questions; low scorers delegated more and more. Hence the predict-first step and the claim-versus-evidence card.
  • PRIMM: predict, run, investigate, modify, make. The ladder follows that order: L1 predicts and investigates, L2 modifies, L3 makes.
  • Agent docs: Claude Code skills, Codex skills, AGENTS.md.
